* 领域：微信生态里的 AI Agent 接入方式

* 现象清单
1. 服务号/订阅号用「客服消息」+ 自建服务器 Webhook，外接大模型做多轮回复
2. 企业微信：群机器人、应用消息、通讯录同步，回调里接 Agent
3. 企业微信「智能机器人」等官方托管能力，配置知识库与对话流
4. 小程序内聊天 UI + 云函数/自建后端调模型，会话上下文在业务库
5. 微信开放平台「对话开放平台」类能力（按产品线演进，对话配置 + 回调）
6. 模板消息、订阅消息、群发：偏「通知型」触达，非自由对话
7. 微信搜一搜、元宝等端内官方 AI，用户不部署、不走自建 Webhook
8. 视频号/微信小店等场景下的客服与自动回复能力
9. 第三方「代开发」模式：服务商一套代码服务多个商户公众号/小程序
10. 非官方「个人号协议/iPad 登录」类接入，外挂 Agent（合规与稳定性风险）
11. 微信支付、统一回调：事件驱动型自动化（偏业务 Agent，非聊天）
12. 小程序插件、JS-SDK：在「微信内网页/小程序」里嵌入能力，仍须回到主体与签名体系

* 降秩过程

** 维度（7 个）
1. *平台与主体谱系*：个人微信 / 公众号·服务号 / 小程序 / 企业微信 / 开放平台服务商 —— 决定「有没有 API、是哪一套 API」。
2. *消息语义类*：实时会话、客服窗口、模板/订阅、应用消息、事件回调 —— 决定「一轮交互长什么样、能否主动触达」。
3. *信令架构*：微信服务器 ↔ 你的服务器的加密回调、被动回复、access_token 体系 —— 决定「工程上怎么接」。
4. *智能与上下文位置*：端内官方模型、云函数、自有 VPC —— 决定「推理与记忆放哪」。
5. *用户触点形态*：会话列表气泡、小程序页、企微工作台、H5 —— 决定「用户从哪进入、UI 能力」。
6. *触达配额与窗口*：48 小时客服、订阅次数、群发限制等 —— 决定「Agent 能骚扰用户到什么程度」。
7. *合规与审核强度*：内容安全、类目、加密模式 —— 决定「哪些回复会被拦」。

** 约束（4 条）
1. *平台谱系 → 消息 API 全集*：知道「是哪一类主体」，就基本确定「能开通哪些消息能力」；消息语义类不是与平台无关的自由组合。（绑 1 ↔ 2）
2. *官方路径 → 信令架构*：凡走微信官方开放接口的对话/通知类接入，必须经过签名、Token、加密包与微信服务器中转；不能绕过「信令架构」单独存在。（绑 3，且与 1 耦合：不同产品线共用同一套安全模型变体）
3. *消息语义类 → 触达配额*：模板/订阅/客服/群内回复，各自有独立配额与窗口规则；知道语义类就大幅压缩「配额」的自由度。（绑 2 ↔ 6）
4. *触点形态 → 技术栈与权限*：小程序内对话与原生会话列表对话，开放能力集不同（支付、文件、录音等）；触点不是纯 UI，与运行环境与鉴权绑定。（绑 5 ↔ 1、4）

** 秩 = 7 - 4 = 3**

独立生成器（生成器之间尽量正交，组合生成现象）：

1. *能力谱系与主体（Platform Lineage）*
   - 人话：你在微信体系里「是谁」——个人号（无官方 Bot API）、公众号/小程序/企微/服务商中的哪一种。
   - 管什么：覆盖现象 1–5、8–10、12 的「能不能接、接哪条产品线」。

2. *异步信令回路（Async Signaling Loop）*
   - 人话：微信把用户动作变成 HTTPS 回调事件，你的 Agent 在外部算完再按接口规范回写；加密、验签、access_token 刷新是这条回路的固定语法。
   - 管什么：覆盖现象 1、2、4、5、9、11、12 的「工程接线形态」；与「端内官方 AI」（现象 7）互斥：官方托管可弱化或省略自建回路。

3. *交互语义与触达契约（Interaction & Reach Contract）*
   - 人话：这一轮是「对话轮次」「通知推送」还是「业务事件」；各自对应的窗口、频率、是否保留多轮上下文由微信规则写死。
   - 管什么：覆盖现象 2、4、6、8、11 的「Agent 像聊天还是像工单/通知」；决定「主动 vs 被动」的可行边界。

* 生成验证

| 现象 | 能否生成 | 用了哪些生成器 |
|------+----------+----------------|
| 1 客服消息 + LLM | ✓ | 能力谱系(公众号) + 异步信令回路(Webhook) + 交互语义(客服轮次) |
| 2 企微群机器人 | ✓ | 能力谱系(企微) + 异步信令回路 + 交互语义(群内 @/应用消息) |
| 3 企微智能机器人 | ✓ | 能力谱系(企微) + 交互语义；信令回路部分内化为官方产品 |
| 4 小程序内对话 | ✓ | 能力谱系(小程序) + 信令回路(业务后端/云函数) + 交互语义(会话型) |
| 5 对话开放平台 | ✓ | 能力谱系(开放平台产品线) + 信令/配置混合 |
| 6 模板/订阅 | ✓ | 能力谱系 + 交互语义(通知契约)，非长对话 |
| 7 元宝/搜一搜 | ✓ | 能力谱系(端内官方) + 交互语义；自建信令回路弱化 |
| 8 视频号小店客服 | ✓ | 能力谱系(电商/客服子能力) + 同上两维组合 |
| 9 第三方代开发 | ✓ | 能力谱系(服务商) + 异步信令回路(多租户回调路由) |
| 10 非官方个人号 | ✓ | 能力谱系(灰产谱系) + 私有信令(非官方) + 交互语义；*不在官方生成器闭合内，属外扩风险分支* |
| 11 支付回调 Agent | ✓ | 能力谱系 + 异步信令(事件非聊天) + 交互语义(业务事件) |
| 12 插件/JS-SDK | ✓ | 能力谱系 + 信令回路(鉴权与 config) + 触点约束 |

*注：现象 10 在「官方秩」之外需要第四条隐含生成器「非官方信源」才能闭合；在合规讨论中通常单独切分。*

* 一句话

微信生态里接入 AI Agent，本质是：先认领「能力谱系」这张牌照，再选「交互语义」这套触达契约，最后用「异步信令回路」（或官方托管替代它）把用户动作接到外置大脑；个人号无牌可领时，一切接法都滑向非官方灰区。
